# MCP Fingerprints Supply Chain & Attestation Benchmark Report

## Executive Summary & Standards Alignment Matrix

This report provides an in-depth comparative benchmark and gap analysis between the current state of `mcp-fingerprints` and modern software supply-chain attestation and SBOM standards, specifically evaluating against Sigstore Cosign, CycloneDX/SPDX, Snyk/Socket.dev, and OpenSSF Scorecard & SLSA Level 3.

As AI agent tool ecosystems (such as MCP) rapidly expand, securing the supply chain of these toolsets is paramount. The analysis reveals that while `mcp-fingerprints` successfully tracks tool structure, it lacks robust cryptographic attestation and comprehensive dependency auditing. To achieve production-grade security and supply-chain integrity, significant architectural enhancements are required.

### Standards Alignment Matrix

| Standard / Framework | Area of Focus | `mcp-fingerprints` Current Alignment | Target Capability |
| :--- | :--- | :--- | :--- |
| **Sigstore Cosign** | Cryptographic Attestation | None. Hashes exist but lack verifiable signatures. | Sign canonical hashes using OIDC tied to GitHub Actions. Log to Rekor. |
| **CycloneDX / SPDX** | AI Tool SBOMs | Ad-hoc structure tracking (`ServerPackageSpec`). | Emit standard CycloneDX BOMs for MCP tools as components. |
| **Snyk / Socket.dev** | Dependency Auditing | None. No dependency or behavior analysis. | Audit dependencies; isolate structural tracking from vulnerability feeds. |
| **OpenSSF / SLSA L3**| Reproducible Builds | Basic AST-to-hash tracking. No verifiable build provenance. | Full SLSA Level 3 compliance for provenance and source-to-hash verification. |

## Technical Findings by Severity

### 🔴 High Severity Gaps

1. **Lack of Cryptographic Attestation (Sigstore / Cosign)**
   - **Current State:** Passports generate canonical SHA-256 hashes for toolsets, but these hashes are not cryptographically signed.
   - **Gap:** There is no mechanism to prove that a specific version of a passport was generated by the trusted `mcp-fingerprints` CI/CD pipeline.
   - **Impact:** Malicious actors could inject tampered `passports.json.gz` files or spoof tool signatures without detection, as there is no verifiable chain of trust.

2. **Absence of Standardized AI Tool SBOMs (CycloneDX/SPDX)**
   - **Current State:** `mcp-fingerprints` uses proprietary JSON schemas (`ServerPackageSpec`) to track tool definitions and ASTs.
   - **Gap:** Tool definitions are not exported into standard CycloneDX or SPDX formats.
   - **Impact:** Integration with enterprise vulnerability management systems (e.g., Dependency-Track) is impossible out-of-the-box. MCP tools cannot be audited alongside traditional software components.

### 🟡 Medium Severity Gaps

1. **Incomplete Reproducible Builds & Provenance (SLSA Level 3)**
   - **Current State:** The system tracks AST-to-hash mappings, but lacks formal build provenance metadata.
   - **Gap:** The CI pipeline does not generate SLSA in-toto attestations for the extraction and validation phases.
   - **Impact:** Users cannot cryptographically verify that the tool definitions perfectly match the origin repository's source code at a specific commit.

2. **Integration vs. Separation of Vulnerability Feeds**
   - **Current State:** Structural tracking is currently the sole focus; vulnerability data (like OSV advisories) is missing.
   - **Gap:** The system needs a defined separation between structural tool passports (identity) and vulnerability advisories (risk).
   - **Impact:** Security scanning tools must rely on generic dependency mapping rather than MCP-specific behavioral or tool-level vulnerability advisories.

### 🟢 Low Severity Gaps

1. **Lack of Dynamic Dependency Auditing (Socket.dev / Snyk)**
   - **Current State:** Static AST extraction does not evaluate dynamic dependency behavior or network access profiles.
   - **Gap:** No metadata is collected regarding the risk profile of the underlying dependencies used by the MCP tools.
   - **Impact:** While not the primary focus of a fingerprinting tool, lacking this metadata means secondary risk engines have less context when evaluating an MCP server.

## Architecture Specification for Sigstore Attestations in mcp-fingerprints passports

To bridge the cryptographic attestation gap, `mcp-fingerprints` must integrate with the Sigstore ecosystem. The following architecture specifies how to implement keyless signing within the `passports.json.gz` distribution lifecycle.

### 1. Attestation Data Model

The `ServerPackageSpec` (or an enveloping signature object) must be extended to include an `attestations` block for each tracked version.

```json
{
  "package_name": "example-mcp-server",
  "versions": {
    "1.0.0": {
      "canonical_hash": "sha256:abcd1234...",
      "attestations": {
        "sigstore": {
          "signature": "base64-encoded-signature",
          "certificate": "base64-encoded-oidc-cert",
          "rekor_bundle": {
            "logIndex": 1234567,
            "integratedTime": 1690000000
          }
        }
      }
    }
  }
}
```

### 2. Signing Workflow (GitHub Actions CI/CD)

The existing `.github/workflows/daily_sync.yml` must be modified to include the `sigstore/cosign-installer` and leverage OIDC tokens.

1. **Extraction & Hashing:** `mcp-fingerprints` completes the AST parsing and generates the canonical SHA-256 hash for the MCP toolset.
2. **Keyless Signing:** Using the GitHub Actions OIDC identity (`id-token: write`), Cosign generates an ephemeral keypair and requests a certificate from the Fulcio Certificate Authority.
3. **Transparency Logging:** The signature and certificate are published to the Rekor transparency log.
4. **Passport Enrichment:** The resulting signature, certificate, and Rekor bundle are injected into the JSON passport before gzip compression.

### 3. Verification Workflow (Client Side)

When a client or agent runtime ingests an MCP tool, it should verify the fingerprint:

1. **Hash Recalculation:** The client recalculates the canonical hash of the local MCP toolset.
2. **Signature Verification:** The client extracts the `signature` and `certificate` from the passport.
3. **Identity Check:** The client verifies that the certificate was issued by Fulcio and that the Subject Alternative Name (SAN) matches the trusted GitHub Actions workflow (`https://github.com/owner/mcp-fingerprints/.github/workflows/daily_sync.yml`).
4. **Transparency Check:** (Optional but recommended) The client queries Rekor using the `rekor_bundle` to ensure the signature was logged during the certificate's validity window.
